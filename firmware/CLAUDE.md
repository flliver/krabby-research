# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

This is the `firmware/` subtree of krabby-research; see the repo-root `CLAUDE.md` for the overall stack. Everything here concerns the three Arduino Mega 2560 motor-driver boards and the host-side Python that talks to them over serial.

## Commands

All `make` targets run from this directory (or `make -C firmware …` from the repo root). Requires `arduino-cli` on PATH and `pyserial` for port auto-detect.

```bash
make compile-firmware                              # compile only (hex lands in build/)
make upload-firmware [PORT=/dev/ttyACM0] [PIN_REV=1]   # compile + flash local board
make flash-remote REMOTE=user@orin PORT=/dev/ttyACM0   # compile here, avrdude over SSH
make flash-remote-all REMOTE=jetson                # flash every board discovered by USB VID:PID
make sync-remote REMOTE=krabby-orin                # rsync host-side Python only, no reflash
```

Unit tests live at the repo root, run without Docker:

```bash
testenv/bin/pytest tests/unit/firmware/ -v
testenv/bin/pytest tests/unit/firmware/test_cli.py -v
```

**Guard tests parse the C++ source.** Several tests (`test_floating_rx_guard.py`, `test_hall_guard.py`, `test_jointcal_guard.py`, `test_makefile_build_flags.py`, `test_calibrate_*.py`) read `arduino/*.ino/.h` and the Makefile as text and assert on their structure. Editing the sketch or Makefile can break Python tests — always run `tests/unit/firmware/` after touching either, and update the guard test when a guarded invariant legitimately changes.

Host CLI: `krabby-firmware <subcommand>` (or `python -m firmware.cli`); `python -m firmware` opens the interactive bench menu; `python -m firmware.gui` is the Tk bench GUI.

## Build invariants

- The Makefile bakes `-DSERIAL_RX_BUFFER_SIZE=256 -DKRABBY_PIN_REV=<n>` into every compile so make/CI/IDE builds are byte-identical. Don't remove these; the RX-buffer define is defensive (a no-op on AVR core 1.8.7, which already defaults the Mega to 256) — see `COMMS_DEBUG.md`.
- Pin wiring is compile-time: `KRABBY_PIN_REV` in `arduino/board_pins.h` (default 3 = Uno v0.2, matches `MOTOR_HEADER_PINOUT.md`).
- `version.h` is generated by `scripts/gen_version_h.py`; CI publishes builds to the public S3 bucket via `scripts/publish_firmware.py` + `manifest.py` (consumed by `cmd_update` and the bench watchdog).

## Architecture

### One image, three boards, roles in EEPROM

A single sketch (`arduino/arduino.ino` + headers) is flashed identically to all boards. Role (`FRONT`/`LEFT`/`RIGHT`, or `UNKNOWN` when blank) and per-board serial live in EEPROM and select which 6 of the 18 joints the board drives (`eepromLoad()` → `applyRole()`). Two independent EEPROM blocks, both CRC-validated (`arduino/eeprom_layout.h`):

- `EepromLayout` at addr 0, magic `0x4B17` — role + serial.
- `JointCalBlock` at addr 64, magic `0xCA17` — per-joint calibration. Kept separate so writing cal never clobbers the role.

### Leader/follower serial topology

On the assembled robot only FRONT is on USB; LEFT/RIGHT hang off FRONT's Serial1/Serial2. FRONT forwards bare command lines downstream and relays follower telemetry/ERR lines upstream via `forwardFullLines()`. Host-side addressing mirrors this: `--port` talks to a board directly (bench/USB hub), `--board left|right` routes through FRONT.

**Hard-won loop() rule:** never drain a serial port with an unbounded `while (available())` — a dangling/floating RX line picks up EMI and produces an endless byte stream that starves the actuator update and USB handling (root cause #1 in `COMMS_DEBUG.md`, enforced by `test_floating_rx_guard.py`). Keep drains bounded per tick.

### Wire protocol (host ↔ board, 115200 baud, newline-terminated lines)

Commands in: `T <joint> <val>…` (position targets, parsed by `command.h`), `J`/`B` (jog / batch jog, watchdog-guarded), `SET`/`GET` (EEPROM config), `CAL…` (calibration), `V` (version — leader aggregates all three boards into one `VER` reply). Telemetry out: one line per tick, `<ROLE>; <name> <pos> <pot> <current> <enL> <enR> <pwmL> <pwmR> <saf>; …`.

**Two contracts must stay in sync by hand:**
- Telemetry: `LinearActuator::printTelemetry` in `arduino/actuator_manager.h` ↔ parser `interfaces/joint_telemetry.py`.
- Command/reply framing: sketch handlers in `arduino.ino` ↔ builders/parsers in `krabby_mcu.py` (`build_set_line`, `parse_get_reply`, `parse_cal_reply`, …).

Read `SETUP.md` (wiring, protocol detail) and `COMMS_DEBUG.md` (root-caused failure history) before changing serial protocol or timing-sensitive code.

### Host-side Python layout

- `krabby_mcu.py` — `KrabbyMCUSDK`: background reader thread parses telemetry/ERR lines into latest-state dicts; all commands (jog, calibrate, set/get, observe) go through it.
- `cli.py` + `__main__.py` — `krabby-firmware` subcommands (`show`, `update`, `set`, `get`, `calibrate-joint`, `calibrate-all`, `validate-current-sense`, `get-calibration`, `jog`, `observe`) plus the interactive menu.
- `mcu_port.py` / `scripts/detect_mcu_port.py` / `scripts/list_mcu_ports.py` — board discovery by USB VID:PID (never bare `/dev/tty*` globs).
- `observation_mapping.py` — raw telemetry → HAL observation transforms (per-leg current → contact_forces, joint-velocity EMA). **Deliberately dependency-free** (no numpy/torch): both the Jetson HAL server and the lightweight `observe` command import it. Keep it that way.
- `interfaces/joint_telemetry.py` — the telemetry line parser (wire-contract peer of `actuator_manager.h`).
- `tools/serial_tcp_bridge.py` — serial-over-TCP for remote debugging. Auto-launched over ssh by `python -m firmware.gui --remote <host>` (`gui/remote.py`), which tunnels a local port, ties the bridge's lifetime to the GUI via stdin-EOF, and takes over stale bridge instances by pidfile. Runs by path on the bench host, so bridge changes need `make sync-remote` before they take effect.

Packaging quirk: `pyproject.toml` maps this directory to the `firmware` package (`package-dir = {"firmware" = "."}`), so imports are `from firmware import …` even though the directory holds the code directly.
